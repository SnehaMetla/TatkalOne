GITHUB PAGES — HARD CONSTRAINTS
---------------------------------
The prototype is hosted on GitHub Pages. This is a static file host with no server.

DEPLOY MODEL
Only the contents of the Code/ folder are pushed to GitHub. In the deployed
site, Code/ disappears — its contents become the GitHub Pages site root.
Every path, structure decision and fallback below is written against that
model. Do not push Brief/, DesignSystem/, Wireframes/ or the master prompt.

Every architectural decision must respect these constraints:

1. NO SERVER-SIDE ROUTING
   GitHub Pages cannot rewrite URLs. A visitor going directly to:
     https://username.github.io/repo/pages/status.html
   will work fine. But a visitor going to:
     https://username.github.io/repo/status
   will get a 404 because there is no server to resolve it.

   RULE: Never use the History API (pushState / replaceState) for navigation.
   Use hash-based routing (#/screen-name) OR direct .html page links only.
   If using a hash router, implement it entirely in router.js with
   window.location.hash and the hashchange event.

2. ALL PATHS MUST BE RELATIVE
   GitHub Pages serves files under a subpath:
     https://username.github.io/REPO-NAME/
   Absolute paths like /css/base.css will resolve to the root domain and break.

   RULE: Every src, href, and fetch path must be relative to the file that
   resolves it. From index.html at the site root use no leading slash and no
   ../ prefix. From a nested page in /pages step up with ../.
     From index.html at root:
       Right:  <link rel="stylesheet" href="css/base.css">
       Right:  fetch('components/header.html')
     From /pages/status.html:
       Right:  <link rel="stylesheet" href="../css/base.css">
       Right:  fetch('../components/header.html')
     Wrong (any file):
       <link rel="stylesheet" href="/css/base.css">
       fetch('/components/header.html')

3. ALL FILENAMES MUST BE LOWERCASE
   GitHub Pages runs on Linux, which is case-sensitive.
   Header.html and header.html are different files on Linux.
   A link that works on your Windows or Mac machine will 404 on GitHub Pages
   if the case does not match exactly.

   RULE: Every file and folder name must be entirely lowercase, using hyphens
   for spaces. No camelCase, no PascalCase, no underscores in filenames.
     Wrong:  StatusCard.html, OTP_Input.js, ErrorBanner.css
     Right:  status-card.html, otp-input.js, error-banner.css

4. NO SERVER-SIDE LOGIC WHATSOEVER
   There is no backend, no PHP, no Node, no .htaccess processing.
   Everything — routing, state, mock data, session — runs in the browser.
   Do not attempt any server-side include, redirect rule, or API call to a
   non-existent backend.

5. 404 FALLBACK
   Create a 404.html at the top of Code/ (which becomes the deployed site
   root). GitHub Pages serves this automatically when a URL cannot be
   resolved. Return the visitor to index.html with an <a href="./"> link and
   an optional <meta http-equiv="refresh" content="1;url=./">.

6. JEKYLL OPT-OUT
   Add an empty .nojekyll file at the top of Code/. Without it, GitHub Pages
   runs the site through Jekyll, which can skip files under folders that
   start with an underscore and rewrite paths.

7. NO file:// TESTING
   ES modules and fetch() do not work when index.html is opened by
   double-click. Always test through a local HTTP server
   (python3 -m http.server 8080 is enough).

ROUTING
-------
Use one of these two approaches. Pick one and use it consistently — never mix them.

OPTION A — Direct page links (simplest, recommended for most builds):
  Every screen is its own .html file in /pages.
  Navigate using standard <a href="../pages/status.html"> links.
  No router.js needed.
  Deep links work on GitHub Pages because the files physically exist.

OPTION B — Hash routing (for single-page feel):
  All screens render inside a single <div id="app"> in index.html.
  router.js listens to window.addEventListener('hashchange', ...) and
  renders the correct view based on window.location.hash.
  Links use href="#/screen-name" format.
  No pushState. No replaceState. Never.

Either way: every navigation action must produce a URL the reviewer can bookmark, share, and reload without getting a 404.


COMPONENT LOADING
-----------------
Components are loaded via fetch() with relative paths. Centralise this in ui.js:

  // ui.js
  async function loadComponent(targetSelector, relativePath) {
    const response = await fetch(relativePath);
    const html = await response.text();
    document.querySelector(targetSelector).innerHTML = html;
  }

Call it from each page's JS file using paths relative to that page's location:
  loadComponent('#header', '../components/header.html');
  loadComponent('#error-banner', '../components/error-banner.html');

Components must be parameterisable via data attributes set before or after load:
  element.dataset.title = 'Upload failed';
  element.dataset.message = 'File must be between 10–20 KB';
  element.dataset.nextStep = 'Compress your photo and re-upload';

Never hardcode content inside a component file. Content comes from the calling page.


BEFORE YOU WRITE A SINGLE LINE OF CODE
---------------------------------------
Read rules.txt in full. Every constraint there applies to every decision you make.
Key ones that directly affect code:

- Mock data must be labelled in the UI. Add a visible closeable "DEMO MODE" banner on every page.

CITIZEN JOURNEY — HOW TO BUILD IT
-----------------------------------
Structure every flow around these six screen types. Build them in this order:

  1. ENTRY / ONBOARDING
     - Clear headline: what this service does and who it is for.
     - Minimal fields. Only ask what is needed for this step.
     - If login is required, display mock credentials visibly on the screen.
       Example: small note at the bottom — "Demo login: user@demo.in / demo1234"

  2. HIGHEST-STAKES ACTION SCREEN
     - This is the screen where the current government experience fails hardest.
       e.g. payment confirmation, OTP entry under time pressure, file upload.
     - This screen gets the most design and code attention.
     - Show a persistent progress indicator so the user always knows where they
       are in the journey.

  3. PENDING / LOADING STATE
     - Never show a blank screen while something is processing.
     - Show exactly what is happening: "Verifying your details...",
       "Connecting to server...", "Saving your progress..."
     - Add a timeout fallback — if mock processing exceeds 8 seconds, show a
       "Taking longer than usual" message with options, not a frozen screen.

  4. SUCCESS STATE
     - Make it unambiguous. Use a distinct colour, icon, and confirmation text.
     - Show a reference number or summary of what was completed.
     - Offer a clear next action: download receipt, track status, return home.

  5. ERROR STATE
     - Every error must include all four of these:
         • What went wrong (plain language, not a system code)
         • Who owns the problem (the system, the user, or a third party)
         • What the user should do next (specific action, not "try again")
         • How long it might take to resolve (even a rough estimate)
     - Example: "Your photo could not be uploaded. It must be between 10–20 KB.
       Your current file is 85 KB. Compress it here → [link] and re-upload."
     - Never show: "Error 500", "Something went wrong", or "Please try again."

  6. RECOVERY / FALLBACK SCREEN
     - If the primary path fails, what happens next?
     - Offer an alternative: a helpline number, a download link, a saved draft
       the user can return to without starting over.
     - Saved progress must be retrievable from browser cache on return.


MOCK DATA
---------
- All mock data lives in /js/mock-data.js. Never hardcode data into HTML or
  other JS files.
- Structure mock data to reflect real Indian formats:
    • Names with regional orders and transliteration variants
      e.g. "Priya R Sharma" and "Priya Ramesh Sharma" are the same person —
      the system must not treat them as different.
    • Phone numbers in +91 format
    • Dates in DD/MM/YYYY
    • Amounts in ₹ with Indian number formatting (1,00,000 not 100,000)
    • Reference/application numbers matching the platform's real format
      e.g. EPFO UAN: 12-digit, IRCTC PNR: 10-digit, GST GSTIN: 15-character
- Label every mock interaction in the UI. Use a small "(DEMO)" tag or muted text.
- Mock OTPs must be pre-filled or displayed visibly so the reviewer can proceed.
  Example: show "For this demo, your OTP is 845621" inline on the screen.
- Never use real Aadhaar numbers, real PANs, or any real personal data.


CAPTCHA SIMULATION
------------------
- Do not block the citizen journey with a real CAPTCHA implementation.
- Where a CAPTCHA would exist in the real service, simulate it:
    • Show the CAPTCHA UI element visually (checkbox, image, or slider).
    • Auto-pass it after a short delay (1–2 seconds) or on any user interaction.
    • Display a small label: "(CAPTCHA simulated for demo)"
- The purpose is to show the reviewer that you accounted for this step —
  not to make them solve one.


SESSION & STATE MANAGEMENT
---------------------------
- Use browser cache (localStorage or sessionStorage) to hold all session state.
  Do not rely on in-memory variables alone — a page refresh must not wipe the journey.
- Use sessionStorage for data that should clear when the tab closes
  (e.g. OTP verification status, active form progress).
- Use localStorage for data that should persist across sessions
  (e.g. a saved draft, a previously completed step).
- At the start of each flow, check browser cache for an existing session and
  resume from where the user left off. Never silently restart.
- State keys must be namespaced to avoid collisions:
  e.g. "bwmi_irctc_booking_step" not just "step".
- Clear all session data on explicit logout or on journey completion.


NETWORK & PERFORMANCE
----------------------
- Simulate real Indian network conditions in mock flows.
  Add artificial delays (1.5s–3s) to any action that would hit a real server.
  Use setTimeout — it makes loading states testable and honest.
- Lazy-load images and non-critical assets using loading="lazy" on <img> tags.
- Compress all images before adding to /assets. Target under 100KB per image.
- Test at throttled speed (Chrome DevTools → Network → Slow 3G) before
  considering any screen done.
- Avoid loading more than 2 external CDN resources. Each one is a failure point
  on a slow connection. If a CDN resource fails to load, the page must still
  be usable — do not depend on CDN assets for core functionality.


ACCESSIBILITY
-------------
- Every interactive element must be keyboard-navigable (Tab, Enter, Space).
- Every form field must have a visible <label>. No placeholder-only fields.
- All status changes (success, error, loading) must be announced to screen
  readers using aria-live="polite" or aria-live="assertive" where urgent.
- Colour must never be the only way to communicate state. Always pair colour
  with an icon and a text label.
  e.g. ✓ Confirmed in green — not just a green background with no text.
- Minimum tap target size: 44×44px for all buttons and links on mobile.
- Minimum font size: 16px for body text. Never go below 14px for any label.
- Test with browser zoom at 150% — the layout must not break or overflow.


RESPONSIVENESS
--------------
- Desktop-first. Build the Desktop layout first, then adapt download smoothly.
- Feel free to collapse or hide few information on phone but it's need to feel forced.
- Breakpoints: 320px, 375px, 414px (mobile), 768px (tablet), 1024px+ (desktop).
- All media queries go in /css/responsive.css only.
- Test on Chrome DevTools at 375px width before finalising any screen.
- Touch targets must not overlap. Leave at least 8px between interactive elements.
- Cap the main content width at 1440px and centre it on larger screens so the layout does not stretch or break on wide monitors.


CSS RULES
---------
- Define all colours, font sizes, spacing units, and border radii as CSS custom
  properties in base.css under :root { }.
- Never use magic numbers in CSS. Use variables.
    Wrong:  padding: 16px;
    Right:  padding: var(--space-md);
- No !important unless overriding a CDN library.
- State classes (is-loading, is-error, is-success, is-disabled) go in states.css
  and are toggled via JS. Never duplicate state logic in component CSS.
- All file names lowercase with hyphens: error-banner.css not ErrorBanner.css.


JS RULES
--------
- No inline event handlers. No onclick="..." in HTML.
- Use addEventListener exclusively, attached in the relevant .js file.
- Keep DOM manipulation out of flow files. Flow files handle logic only.
  DOM updates go through functions in ui.js.
- Use const and let only. No var.
- Comment every function: what it does, what it takes, what it returns.
- If a function exceeds 30 lines, it is doing too much. Split it.
- All file names lowercase with hyphens: mock-data.js not mockData.js.
